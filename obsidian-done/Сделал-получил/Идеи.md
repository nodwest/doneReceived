## Аккаунт ребёнка: коды привязки устройства

Разберу по шагам: что видит каждый, что создаётся на сервере, что передаётся и где хранится.

## Что меняется в кодах

**Сейчас** у семьи два постоянных кода (`inviteCodesMock`):
- `PAR7-…` — «вступить в семью Miller как родитель»;
- `KID4-…` — «вступить в семью Miller как ребёнок». Каждый ввод создаёт **нового** ребёнка, отсюда и дубли.

**Предлагаю:**
- **Код родителя остаётся как есть.** Он постоянный, один на семью, второй родитель входит по нему. У родителя свой аккаунт с почтой, поэтому дублей там не бывает.
- **Общего детского кода больше нет.** Вместо него появляется **код привязки устройства**. Он выдаётся под конкретного ребёнка (Emma), одноразовый и действует около 15 минут. По смыслу это «временный пароль от аккаунта Emma».

Главное отличие: старый детский код отвечает на вопрос «в какую семью вступить», новый — «в чей аккаунт войти». Поэтому новый код не может создать ребёнка, он только впускает в уже созданный профиль.

## Что хранит сервер

| Таблица | Поля | Комментарий |
|---|---|---|
| `families` | id, фамилия, постоянный код родителя | как сейчас |
| `parents` | id, familyId, почта, хэш пароля | как сейчас |
| `children` | id, familyId, имя, аватар, баланс… | **без почты и пароля** |
| `child_link_codes` | код, childId, expiresAt, usedAt | живут минуты, после ввода помечаются использованными |
| `sessions` | id, кто (parent/child + id), хэш refresh-токена, название устройства, lastSeen | одна запись на каждое подключённое устройство |

## Сценарий А: ребёнок подключается впервые

**Шаг 1. Родитель создаёт профиль ребёнка**
- *Где:* Family → «+ Family member» → `InviteCodesPanel`. Карточка «Код ребёнка» заменяется кнопкой «Добавить ребёнка» с формой: имя и аватар.
- *Запрос:* `POST /children { name, avatar }`.
- *Сервер:* создаёт запись в `children` (Emma, баланс 0) и возвращает её.
- *Клиент родителя:* инвалидирует список детей. Карточка Emma появляется на Family с пометкой «Устройство не подключено». Задачи ей можно назначать уже сейчас.

**Шаг 2. Родитель получает код для Emma**
- *Где:* сразу после создания или позже из профиля Emma, кнопка «Подключить устройство».
- *Запрос:* `POST /children/:id/link-code`.
- *Сервер:* генерирует код, сохраняет в `child_link_codes` строку «код → Emma, действует до 15:15» и возвращает `{ code, expiresAt }`.
- *Что видит родитель:* код в `CopyableCode`, под ним «Действует ещё 14:59» и кнопка «Новый код». Можно добавить QR.
- *Хранение у родителя:* только в памяти экрана (кэш React Query). На диск код не пишется.

**Шаг 3. Передача кода**
Происходит вне приложения: родитель показывает экран, диктует или пересылает код в мессенджере.

**Шаг 4. Ребёнок вводит код**
- *Где:* `role-select` → карточка Kid → `InviteCodeField`, то есть как сейчас.
- *Как только код введён полностью:* `GET /child-link-codes/:code`. Это проверка без входа, аналог сегодняшнего `fetchFamilyInvite`.
- *Сервер отвечает:* `{ childName: 'Emma', familyName: 'Miller', avatar }`, а если код неверный или просрочен — ошибкой.
- *Что видит ребёнок:* зелёная плашка `FamilyFound` с аватаром и текстом «Ты — Emma, семья Miller» (сейчас там «семья Miller, роль ребёнок»). Если код неверный, просрочен или уже использован, показывается ошибка «Попроси у родителя новый код».
- *Continue:* `POST /auth/child/link { code, deviceName }`.
- *Сервер:* ещё раз проверяет код, помечает его использованным (второй раз он не сработает), создаёт запись в `sessions` и возвращает `Session { accessToken, refreshToken, user: { id: emmaId, role: 'child', … } }`.
- *Клиент ребёнка:* `useSessionStore.signIn(session)` кладёт сессию в secure-store, то есть ровно туда же, куда сейчас кладётся сессия родителя. Дальше режим ребёнка и переход на `/`.

**Шаг 5. Родитель видит результат**
Карточка Emma меняется на «Подключено · iPhone Emma».

## Сценарий Б: обычный запуск

- `root-layout` вызывает `restore()` и находит сессию в secure-store. Если в ней `role: 'child'`, ребёнок сразу попадает на свою главную.
- Когда `accessToken` истекает, клиент тихо вызывает `POST /auth/refresh { refreshToken }` и получает новый.
- Ребёнок никаких кодов не видит. Код нужен только при подключении нового устройства.

## Сценарий В: переустановка приложения

1. Ребёнок удалил приложение, secure-store очистился (на Android точно, на iOS обычно тоже, если специально не сохранять).
2. После установки открывается `role-select` → Kid → поле кода.
3. Родитель: Family → карточка Emma → профиль → «Подключить устройство». Это тот же запрос `POST /children/:id/link-code`, что в шаге 2, и он выдаёт **новый** код для **той же** Emma.
4. Ребёнок вводит код, видит «Ты — Emma», нажимает Continue и получает сессию с тем же `emmaId`. Баланс, вишлист и история на месте, второго ребёнка нет.
5. Сессия удалённого приложения осталась на сервере. Есть два решения:
   - сервер закрывает старые сессии Emma при новой привязке (проще, одно устройство на ребёнка);
   - старая сессия остаётся в списке «Устройства Emma», и родитель удаляет её вручную (так можно держать телефон и планшет одновременно).

## Сценарий Г: потерянный телефон

- Родитель: профиль Emma → Устройства → удалить. Запрос `DELETE /children/:id/sessions/:sid`.
- На потерянном телефоне следующий `refresh` получит `401`, клиент вызовет `signOut()` и покажет `role-select`.
- Деньги не пострадают: всё хранится на сервере, войти обратно можно только по новому коду от родителя.

## Почему код одноразовый и короткий по времени

Код привязки фактически заменяет пароль от аккаунта Emma. Если бы он был постоянным, как сейчас, любой, кто однажды его увидел (брат, одноклассник), мог бы войти как Emma. Одноразовый код, который действует 15 минут, после использования ничего не стоит. Поэтому его можно сделать и покороче, например 8 символов.

## Итого: кто что видит

| | Родитель | Ребёнок |
|---|---|---|
| Family → + Family member | постоянный код родителя (как сейчас) и кнопка «Добавить ребёнка» | — |
| Профиль ребёнка | «Подключить устройство» → код с таймером; список устройств | — |
| `role-select` → Kid | — | ввод кода → «Ты — Emma, семья Miller» → Continue |
| Хранится на устройстве | своя сессия | своя сессия (secure-store) |
| Хранится на сервере | всё: профили, коды привязки, сессии | — |

В нашем коде это затронет моки и mock-server в `entities/family` (`child` уходит из `inviteCodesMock`, появляются коды привязки), `InviteCodesPanel`, `features/join-family` (для роли `child` — новые запросы и текст «Ты — Emma») и профиль ребёнка (кнопка «Подключить устройство»).

# Задание для бэкенда: семья, роли и связь аккаунтов

## Зачем это всё

Почти все ручки API работают внутри семьи: `/families/{familyId}/...`. Пока у родителя нет `familyId`, он не может ни добавить ребёнка, ни создать задание. Поэтому порядок такой:

1. Родитель регистрируется и подтверждает почту. Это уже работает.
2. Родитель входит в приложение. Приложение вызывает `GET /families`.
3. Если список пустой, родитель видит экран «Ваша семья» с двумя вариантами:
   - **Создать семью**: вводит название, `POST /families`, становится **owner**;
   - **Вступить в семью**: вводит 8-символьный код `XXXX-XXXX`, который второй родитель видит у себя в Family → «+ Участник семьи» → «Для родителя», `POST /families/join`, становится **admin**.
4. Когда семья есть, приложение открывается как обычно. Дети создаются внутри семьи (`POST /families/{id}/children`) и подключают устройство одноразовым кодом. Это в API уже есть.

Основной сценарий — **один родитель и один или несколько детей**. Второй родитель может появиться, а может и нет. Семья у аккаунта **одна**. Объединять две семьи не будем: второй родитель вступает в уже существующую семью, а не создаёт свою.

Макеты экрана: Figma, файл Untitled, ряд «NEW · Семья после регистрации родителя: создать или вступить».

## Что фронт уже использует

Это уже подключено в приложении, менять не нужно:

| Ручка | Для чего |
|---|---|
| `GET /families` | после входа: есть ли семья. Пустой список — показываем экран «Ваша семья» |
| `POST /families` `{ name }` | кнопка «Создать семью» |
| `POST /families/join` `{ code }` | кнопка «Вступить» |
| `POST /families/{familyId}/invites` | код «Для родителя»: вызываем **только** когда родитель открыл окно «+ Участник семьи» (подробно — п. 3) |

Ниже то, что нужно добавить или изменить, по порядку важности.

## 1. Кто вошёл: `kind` и `family` в профиле пользователя (обязательно)

**Проблема.** В ответах `POST /auth/login`, `POST /auth/refresh` и `GET /users/me` нет ни типа аккаунта (родитель или ребёнок), ни его семьи. Поэтому фронт:

- не знает, какой интерфейс показывать: у родителя и ребёнка разные экраны (сейчас мы переключаем это временным тумблером);
- после каждого входа вынужден делать лишний `GET /families`, только чтобы узнать `familyId`.

**Что сделать.** Добавить в объект пользователя два поля во всех трёх ответах:

```json
{
  "id": "6f1c…",
  "email": "sarah@email.com",
  "displayName": "Sarah",
  "avatarUrl": null,
  "status": "active",
  "kind": "parent",
  "family": {
    "id": "0b7e…",
    "name": "Miller",
    "role": "owner"
  }
}
```

- `kind`: `"parent" | "child"`. Определяет интерфейс.
- `family`: `null`, если семьи ещё нет (родитель только что зарегистрировался), иначе `{ id, name, role }`, где `role` — `"owner" | "admin" | "member"`.

Тот же объект `user` нужно отдавать в ответе `POST /child-devices/pair`. Сейчас там только токены и `deviceId`, и ребёнок после подключения не знает, кто он:

```json
{
  "accessToken": "…",
  "refreshToken": "…",
  "deviceId": "…",
  "user": { "id": "…", "email": null, "displayName": "Emma", "avatarUrl": null, "status": "active", "kind": "child", "family": { "id": "0b7e…", "name": "Miller", "role": "member" } }
}
```

## 2. Коды ошибок в ответах (обязательно)

**Проблема.** В `HttpErrorDto` сейчас только текст. Например, `POST /families/join` отвечает 409 в трёх разных случаях («уже в семье», «не может вступить», «нет мест»), и фронт не может показать человеку, что именно случилось. Текст сервера показывать нельзя: интерфейс переведён на два языка.

**Что сделать.** Добавить в тело ошибки машинное поле `code`, текст оставить для отладки:

```json
{
  "statusCode": 409,
  "code": "ALREADY_IN_FAMILY",
  "message": "Account already belongs to a family"
}
```

Коды по ручкам этой задачи:

| Ручка | HTTP | `code` | Когда |
|---|---|---|---|
| `POST /families` | 400 | `INVALID_FAMILY_NAME` | пустое или длиннее 100 |
| `POST /families` | 409 | `ALREADY_IN_FAMILY` | у аккаунта уже есть семья |
| `POST /families/join` | 400 | `INVITE_NOT_FOUND` | такого кода нет |
| `POST /families/join` | 400 | `INVITE_EXPIRED` | код истёк |
| `POST /families/join` | 400 | `INVITE_USED` | код уже использован |
| `POST /families/join` | 409 | `ALREADY_IN_FAMILY` | аккаунт уже в **непустой** семье (см. п. 6) |
| `POST /families/join` | 409 | `FAMILY_FULL` | достигнут `userLimit` |
| `POST /families/join`, `GET /families/invites/{code}` | 429 | `TOO_MANY_ATTEMPTS` | превышен лимит неверных кодов (п. 3) |
| `POST /families/join` | 409 | `NOT_A_PARENT` | код ввёл детский аккаунт |
| `DELETE /families/{id}/children/{childId}` | 409 | `CHILD_HAS_BALANCE` | у ребёнка есть деньги на счету (п. 7) |
| `DELETE /families/{id}/children/{childId}` | 409 | `CHILD_HAS_PENDING_REVIEW` | есть отчёты на проверке (п. 7) |
| `DELETE /families/{id}/members/me` | 409 | `LAST_PARENT_WITH_CHILDREN` | последний родитель, а в семье есть дети (п. 7) |
| любые `/families/{id}/…` | 403 | `FORBIDDEN_ROLE` | не хватает роли (см. п. 9) |

## 3. Код приглашения родителя: 8 символов, 15 минут, выдаётся по запросу (обязательно)

Договорились на созвоне. Код второго родителя устроен так же, как код подключения устройства ребёнка.

### Формат

- **8 символов**, на экране с дефисом посередине: `PR7Q-2KD8`;
- алфавит без похожих символов: `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (нет `0/O`, `1/I/L`);
- без учёта регистра;
- **живёт 15 минут**, одноразовый: после успешного `join` гаснет.

Сейчас код — 32 символа `[A-Za-z0-9_-]` с учётом регистра. Его нельзя продиктовать по телефону или перепечатать с экрана жены, только скопировать.

### Когда выдаётся

Код **не существует, пока родитель не захотел кого-то пригласить**. Фронт вызывает `POST /families/{familyId}/invites` только в момент, когда родитель нажал «+ Участник семьи» на вкладке Family (или «Коды семьи» в профиле) и открылось окно «Добавить в семью». Без этого запросов нет и кода нет.

Логика на сервере при каждом `POST /families/{familyId}/invites`:

1. У семьи есть **живой** код (не истёк и не использован) — вернуть **его же**, нового не создавать.
2. Живого кода нет (не было, истёк или использован) — **создать новый** на 15 минут и вернуть его.
3. Сам по себе, по таймеру, новый код **не создаётся**. Истёк — значит, кода просто нет до следующего открытия окна.

```http
POST /families/0b7e…/invites
Authorization: Bearer <access token родителя>
```
```json
{ "code": "PR7Q-2KD8", "expiresAt": "2026-11-10T12:15:00.000Z" }
```

- `code` — с дефисом, как показываем на экране.
- `expiresAt` — нужен фронту, чтобы знать, когда код сменится. Пользователю срок не показываем.
- Права: owner и admin, иначе 403 `FORBIDDEN_ROLE`.
- Тело запроса не нужно.

Для пользователя разницы нет: он открывает окно и видит код, который нужно передать второму родителю. Ни таймера, ни кнопки «Новый код» нет. Открыл окно ещё раз через 5 минут — тот же код. Открыл через 20 минут — уже новый.

Если код истёк, пока окно открыто, фронт сам в момент `expiresAt` повторяет тот же `POST`. Живого кода в этот момент нет, поэтому сервер выдаёт новый (правило 2), и в окне появляется актуальный код. Окно открыто, значит, намерение пригласить ещё есть, так что правило «код только по намерению» не нарушается.

### Вступление по коду

```http
POST /families/join
Content-Type: application/json

{ "code": "PR7Q2KD8" }
```

- Фронт отправляет код **без дефиса и заглавными**. Пусть сервер всё равно принимает и `pr7q-2kd8`: отбрасывает дефисы и пробелы и приводит к верхнему регистру.
- Неверный, истёкший и использованный код — 400 с разными `code` (п. 2): `INVITE_NOT_FOUND`, `INVITE_EXPIRED`, `INVITE_USED`.
- Защита от перебора кодов — лимит неверных попыток, см. ниже «Лимит попыток».

### Лимит попыток

**Сейчас лимита нет.** В Swagger у `POST /families/join` нет ответа 429. Лимит запросов стоит только на `/auth/*` и `POST /child-devices/pair`.

**Зачем он нужен.** Код из 8 символов — это 32^8 ≈ 10^12 вариантов. Один код угадать почти невозможно, но злоумышленнику не нужен конкретный код, ему подойдёт **любой** живой. Если одновременно живы 10 000 кодов, без лимита скрипт перебирает тысячи кодов в секунду и рано или поздно попадает в чужую семью, а значит, видит детей, их задания и геопозицию. С лимитом это становится нереально.

**Лимит ставит только сервер.** Фронт его не обеспечит: запросы можно отправлять мимо приложения.

**Что предлагаем:**

| Счётчик | Лимит | Что считаем |
|---|---|---|
| на аккаунт | 10 неверных кодов за 15 минут | неудачные `POST /families/join` и `GET /families/invites/{code}` — **общий** счётчик для обеих ручек |
| на IP | 30 неверных кодов за час | то же; защищает от перебора с многих новых аккаунтов |

**Что считается попыткой.** Одна попытка — один полностью введённый неверный код:

- пока в поле меньше 8 символов, фронт запрос не шлёт;
- ввёл 8-й символ — одна проверка; ошибся в одной цифре и исправил — это ещё одна проверка;
- **один и тот же** неверный код повторно не считать: в счётчик идут разные неверные коды;
- считаем только неверные коды (не найден, истёк, использован); успешная попытка счётчик не трогает.

Почему 10, а не меньше: человек вводит код с чужого телефона и легко ошибается 2–3 раза подряд. Даже 10 попыток за 15 минут — меньше 1000 проверок в сутки с аккаунта, и при 10 000 живых кодов шанс угадать хоть один за сутки порядка 10^-5.

**Сколько осталось.** В ответе на неверный код отдавать `attemptsLeft`. Фронт покажет «Осталось 3 попытки», когда останется 3 и меньше; до этого человек про лимит не знает:

```json
{ "statusCode": 400, "code": "INVITE_NOT_FOUND", "message": "Invite code not found", "attemptsLeft": 3 }
```

**Алфавит помогает.** В коде нет `0`, `O`, `1`, `I`, поэтому фронт не даёт вводить эти символы, и ошибки «ноль вместо О» не бывает.

- Лимит превышен — `429` с `code: "TOO_MANY_ATTEMPTS"` и заголовком `Retry-After` в секундах:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 900
Content-Type: application/json

{ "statusCode": 429, "code": "TOO_MANY_ATTEMPTS", "message": "Too many invalid invite codes" }
```

- Фронт покажет: «Слишком много попыток. Попробуйте через N минут» (N — из `Retry-After`).
- Обе ручки доступны только вошедшему родителю с подтверждённой почтой: каждый новый аккаунт для перебора стоит злоумышленнику регистрации.
- Цифры можно поменять, важно, чтобы лимит был и на аккаунт, и на IP, и был общим для предпросмотра и вступления.

То же стоит сделать для `POST /child-devices/pair`, если там лимит считается по всем запросам, а не по неверным кодам.

### Что поменять на беке

| Было | Стало |
|---|---|
| код 32 символа `[A-Za-z0-9_-]`, регистр важен | 8 символов из алфавита выше, `XXXX-XXXX`, регистр не важен |
| живёт 24 часа | живёт 15 минут |
| каждый `POST /invites` выпускает новый код | `POST /invites` возвращает живой код, новый — только если живого нет |
| `JoinFamilyDto.code`: pattern `^[A-Za-z0-9_-]{32}$` | принимает `XXXXXXXX` и `XXXX-XXXX` в любом регистре |
| лимита на `join` нет | 10 разных неверных кодов за 15 минут на аккаунт, 30 в час на IP, общий с предпросмотром, `attemptsLeft` в ошибке, `429 TOO_MANY_ATTEMPTS` |

## 4. Предпросмотр приглашения (обязательно)

**Проблема.** На экране «Вступить в семью» мы хотим показать, куда человек попадёт, **до** вступления: «Семья Miller · Sarah, Emma, Liam» (зелёная плашка в макете). Сейчас узнать это можно только вступив, а вступление необратимо.

**Что сделать.** Новая ручка, ничего не меняет:

```http
GET /families/invites/PR7Q2KD8
Authorization: Bearer <access token родителя>
```

```json
{
  "familyId": "0b7e…",
  "familyName": "Miller",
```

## 6. Вступление, если родитель случайно создал свою семью (обязательно)

**Сценарий.** Папа скачал приложение, зарегистрировался и по ошибке нажал «Создать семью», хотя жена уже всё настроила. Теперь он в своей пустой семье, и `join` отвечает 409.

**Правило.** Если у аккаунта семья **пустая** (в ней только он сам: нет детей, второго родителя и заданий), `POST /families/join` её тихо удаляет и вступает в новую. Если семья **не пустая**, отвечает 409 `ALREADY_IN_FAMILY`, и родитель сначала выходит из своей семьи сам (п. 7).

```http
POST /families/join
{ "code": "PR7Q2KD8" }
```
```json
{ "familyId": "0b7e…", "leftFamilyId": "9a21…" }
```
`leftFamilyId` — id удалённой пустой семьи, если такая была, иначе `null`.

Сливать две семьи с детьми и историей **не нужно**. Это сложно, рискованно для балансов и почти никогда не понадобится.

## 7. Управление составом семьи (обязательно)

Сейчас из семьи нельзя никого убрать, удалить ребёнка или переименовать что-либо.

### Удалить ребёнка

Главное правило всего приложения — **не потерять деньги ребёнка**. Поэтому удалить можно только ребёнка, у которого на счету ничего нет и ничего не ждёт выплаты.

```http
DELETE /families/{familyId}/children/{childId}
```
→ `204`. Права: **только owner**.

**Когда удалить нельзя.** Сервер отвечает 409 и объясняет причину кодом ошибки:

| Причина | `code` | Что делает родитель |
|---|---|---|
| на счету ребёнка есть деньги (`balancePoints > 0`) | `CHILD_HAS_BALANCE` | сначала выводит все средства ребёнка, баланс становится 0 |
| есть отчёты на проверке (назначения в статусе `submitted`) | `CHILD_HAS_PENDING_REVIEW` | сначала одобряет или отклоняет их: одобрение — это деньги ребёнка, их нельзя потерять вместе с отчётом |

Пример ответа, чтобы фронт показал сумму:

```json
{
  "statusCode": 409,
  "code": "CHILD_HAS_BALANCE",
  "message": "Child has a non-zero balance",
  "balancePoints": "12"
}
```

**Вывод средств.** Сейчас в API нет способа уменьшить баланс ребёнка: кошелёк умеет только начислять баллы за задания. Значит, для удаления нужна ручка вывода, например «родитель выплатил ребёнку деньги наличными или на карту». Она пишет в кошелёк запись со знаком минус и уменьшает баланс. Её формат обсудим отдельно, вместе с кошельком. Без неё удалить ребёнка с ненулевым балансом будет невозможно.

**Что происходит при удалении**, когда баланс 0 и отчётов на проверке нет:

- профиль помечается удалённым (**мягкое удаление**) и пропадает из всех списков;
- все устройства и сессии ребёнка отзываются: на его телефоне следующий запрос получит 401;
- **задания, назначенные на ребёнка, удаляются автоматически**: назначения в статусах `assigned` и `rejected` удаляются. Если задание было назначено нескольким детям, удаляется только назначение этого ребёнка, остальные дети его по-прежнему видят. Если у задания не осталось ни одного назначения, удаляется и само задание;
- история (одобренные задания, начисления, выводы) остаётся в базе: по ней родители видят, сколько и за что выплачено;
- вишлист ребёнка удаляется вместе с профилем;
- повторный вызов тоже возвращает `204`.

**Гонки.** Проверку баланса и удаление нужно делать в одной транзакции с блокировкой кошелька ребёнка. Иначе родитель может одобрить отчёт (начисление) ровно в момент удаления, и деньги окажутся на удалённом профиле.

### Имя и фото: каждый меняет своё сам

Отдельная ручка, чтобы родитель переименовывал ребёнка (`PATCH /families/{id}/children/{childId}`), **не нужна**:

- ребёнок **ещё не подключил устройство** — профиль пустой: заданий он выполнить не мог, денег нет. Ошиблись в имени — удаляем профиль и создаём заново (правила удаления из раздела выше этому не мешают);
- ребёнок **уже подключил устройство** — имя и фото он меняет сам, в своём профиле.

Для этого нужна одна общая ручка «изменить свой профиль». Ей пользуются и родитель (экран Edit profile в приложении уже есть), и ребёнок:

```http
PATCH /users/me
Content-Type: application/json

{ "displayName": "Emma" }
```
→ `200` + `UserResponseDto` (с полями `kind` и `family` из п. 1).

- `displayName` — 1–100 символов, пробелы по краям обрезать, как при регистрации.
- Доступна любому вошедшему аккаунту, меняет только его самого.
- Новое имя сразу видно в семье: в `GET /families/{id}/members` и `GET /families/{id}/children`.

Фото — отдельной ручкой, можно позже:

```http
PUT /users/me/avatar
Content-Type: multipart/form-data

photo=<PNG или JPEG до 2 МиБ>
```
→ `200` + `UserResponseDto` с новым `avatarUrl`.

```http
DELETE /users/me/avatar
```
→ `204`, фото убирается.

### Убрать второго родителя

```http
DELETE /families/{familyId}/members/{memberId}
```
→ `204`. Права: **только owner**, себя так удалить нельзя (400 `CANNOT_REMOVE_SELF`). Сессии удалённого не отзываем: он просто остаётся без семьи и после входа увидит экран «Ваша семья».

### Выйти из семьи самому

```http
DELETE /families/{familyId}/members/me
```
→ `204`.

**admin** выходит свободно.

**owner уходит — владение переходит само.** Обсудили с беком: если owner выходит из семьи (или удаляет свой аккаунт), права owner автоматически передаются другому родителю. Семья никогда не остаётся без владельца, и человеку не нужно сначала разбираться с передачей владения.

Кому передаётся, когда родителей больше двух: **родителю, который раньше всех вступил в семью** (самое раннее членство `admin`). Правило простое и предсказуемое, его легко показать в интерфейсе заранее: «Вы выйдете из семьи. Владельцем станет George».

Если owner хочет передать владение кому-то другому, он делает это до выхода существующей ручкой `POST /families/{familyId}/members/{memberId}/transfer-ownership`.

Ответ на выход owner, чтобы фронт показал, кто стал владельцем:

```json
{ "newOwnerMemberId": "…", "newOwnerUserId": "…" }
```

(или `204` без тела, если owner был единственным участником; тогда семья удаляется).

**Последний родитель не может уйти, пока в семье есть дети.** Иначе дети с деньгами на счету останутся в семье без родителей, и выплатить им будет некому. Ответ — 409 `LAST_PARENT_WITH_CHILDREN`. Сначала родитель удаляет детей (по правилам выше: баланс 0, отчётов на проверке нет), потом уходит, и семья удаляется.

Итого:

| Кто выходит | Что происходит |
|---|---|
| admin | выходит, остальное не меняется |
| owner, есть другие родители | владение переходит к родителю, который вступил раньше всех; owner выходит |
| owner, других родителей нет, детей нет | выходит, семья удаляется |
| owner, других родителей нет, есть дети | 409 `LAST_PARENT_WITH_CHILDREN` |

### Переименовать семью

```http
PATCH /families/{familyId}
{ "name": "Miller" }
```
→ `200` + `FamilyResponseDto`. Права: owner и admin.

### Удалить семью

```http
DELETE /families/{familyId}
```
→ `204`. Права: только owner, и только когда в семье больше никого нет (иначе 409 `FAMILY_NOT_EMPTY`). Детей сначала удаляют по правилам выше, так что деньги при удалении семьи потеряться не могут.

## 9. Роли и права

Новых ролей не нужно, хватает тех, что уже есть в API. Нужно только зафиксировать права.

- **`kind`** (`parent` / `child`) определяет, **какой интерфейс** видит аккаунт.
- **`role`** в семье определяет, **что можно делать**:
  - `owner` — создал семью. Один на семью;
  - `admin` — второй родитель, вступил по коду;
  - `member` — ребёнок.

`owner` нужен ровно для одного: чтобы двое равных родителей не могли удалить друг друга или всю семью. Если родитель один, он просто owner, и разницы никто не замечает. В остальном второй родитель может всё то же, что и первый.

| Действие | owner | admin | member (ребёнок) |
|---|:-:|:-:|:-:|
| Создавать задания | ✅ | ✅ | — |
| Проверять, выплачивать, править и отменять **свои** задания | ✅ | ✅ | — |
| Добавлять ребёнка | ✅ | ✅ | — |
| Выдавать код устройства ребёнка, отключать устройства | ✅ | ✅ | — |
| Выдавать и отзывать код для второго родителя | ✅ | ✅ | — |
| Переименовать семью | ✅ | ✅ | — |
| Менять своё имя и фото (`PATCH /users/me`) | ✅ | ✅ | ✅ |
| **Удалить ребёнка** (только при балансе 0 и без отчётов на проверке) | ✅ | ❌ | — |
| **Убрать второго родителя** | ✅ | ❌ | — |
| **Передать владение, удалить семью** | ✅ | ❌ | — |
| Выйти из семьи | ✅ владение само переходит к родителю, который вступил раньше всех; последний родитель не уходит, пока есть дети | ✅ | — |
| Видеть состав семьи | ✅ | ✅ | ✅ (только чтение) |
| Отправлять отчёты по своим заданиям | — | — | ✅ |
| Вести свой вишлист | — | — | ✅ |

Проверять и выплачивать задание может **только его автор** (`createdBy`), даже если второй родитель тоже admin. Так это уже устроено во фронте. Второй родитель видит чужие задания, но не проверяет их.

## 11. Использованный код сразу заменяется новым (обязательно)

**Что сейчас.** По Swagger обе ручки выдачи кодов возвращают **тот же** код до конца 15 минут, даже если код уже использован:

- `POST /families/{familyId}/children/{childId}/device-codes` — «Повторный запрос возвращает тот же код до истечения срока». В ответе `used: true`, но код прежний;
- `POST /families/{familyId}/invites` — «Повторный запрос до истечения срока возвращает ту же пару». В ответе `parentUsed: true`, но `parentCode` прежний.

**Что из-за этого видит родитель.** Ребёнок подключил устройство по коду `K7QM2LP8`. Через минуту родитель открывает «Подключить устройство», чтобы подключить ему планшет, и видит тот же `K7QM2LP8` с таймером «осталось 14 минут». Этот код уже погашен и не сработает: ребёнок получит «код истёк или уже использован». Новый код родитель получить не может, пока не пройдут оставшиеся 14 минут. Так же со вторым родителем: после вступления окно «+ Участник семьи» ещё 15 минут показывает погашенный код.

**Как должно быть.** 15 минут код живёт, **пока его не использовали**: это нужно, чтобы при каждом открытии окна не создавать новый код. Использованный код больше ни для чего не нужен, поэтому при следующем запросе сервер сразу выдаёт новый.

Правило для обеих ручек при каждом `POST`:

| Текущий код | Что вернуть |
|---|---|
| есть, не истёк и **не использован** | его же, с прежним `expiresAt` |
| истёк | новый код на 15 минут |
| **использован** (даже если 15 минут ещё не прошли) | **новый** код на 15 минут |
| кода не было | новый код на 15 минут |

Это то же правило «живой код», что в п. 3: живой — это **не истёк и не использован**.

### Код устройства ребёнка

```http
POST /families/{familyId}/children/{childId}/device-codes
```

Было:
```json
{ "code": "K7QM2LP8", "expiresAt": "2026-11-10T12:15:00.000Z", "used": true }
```

Должно быть, если `K7QM2LP8` уже погашен:
```json
{ "code": "X4TR9BN2", "expiresAt": "2026-11-10T12:21:00.000Z", "used": false }
```

Поле `used` в ответе после этого всегда будет `false`. Его можно оставить или убрать, фронт его не читает.

### Код второго родителя

```http
POST /families/{familyId}/invites
```

Сейчас коды выдаются парой с общим сроком (`parentCode` + `childCode`, один `expiresAt`). Если `parentCode` погашен, выдать новый `parentCode` с новым сроком. Проще всего выдать новую пару целиком: общий детский код `childCode` фронт не показывает (ребёнка добавляет родитель через Add a child, см. обсуждение варианта A).

**Что делает фронт.** Код у себя не запоминает: каждое открытие окна «Подключить устройство» или «+ Участник семьи» отправляет `POST` и показывает то, что вернул сервер. Поле `used` / `parentUsed` фронт не проверяет — показывать погашенный код или нет, решает сервер по правилу выше.

**Как проверить:**

1. `POST …/device-codes` → код A. Повторный `POST` сразу → снова A, `expiresAt` тот же.
2. Подключить устройство кодом A (`POST /child-devices/pair`).
3. `POST …/device-codes` → **новый** код B со своим сроком 15 минут.
4. То же для `POST /invites`: вступить вторым родителем по `parentCode` → следующий `POST /invites` отдаёт **новый** `parentCode`.

## Порядок работ и проверка

1. **п. 1 и 2** (`kind`/`family` в пользователе, коды ошибок). Без них фронт не может правильно маршрутизировать после входа.
2. **п. 3 и 4** (код 8 символов на 15 минут, выдача по запросу, предпросмотр). Без них второй родитель вступает в семью вслепую. П. 5 (отзыв кода) — по желанию.
3. **п. 6 и 7** (пустая семья при вступлении, управление составом).
4. **п. 8** и проверки ролей из **п. 9** во всех ручках.
5. **п. 11** (использованный код сразу заменяется новым) — сейчас родитель после подключения устройства видит погашенный код.
6. **п. 10** — когда будет время.

Как проверить весь путь:

1. Зарегистрировать Sarah и подтвердить почту. В `POST /auth/login` → `user.family === null`.
2. `POST /families { "name": "Miller" }` → в `GET /users/me` `family.role === "owner"`.
3. `POST /families/{id}/children { "displayName": "Emma" }`.
4. `POST /families/{id}/invites` → код `XXXX-XXXX` и `expiresAt` через 15 минут. Повторный `POST` сразу → **тот же** код. Через 15 минут `POST` → **новый** код. После вступления по этому коду (шаг 5) `POST` → тоже **новый** код (п. 11).
5. Зарегистрировать George. `GET /families/invites/{code}` → «Miller, Sarah, Emma». `POST /families/join { "code": "pr7q-2kd8" }` (строчными, с дефисом) → `family.role === "admin"`. Тот же код ещё раз → 400 `INVITE_USED`.
6. George: `DELETE /families/{id}/children/{emmaId}` → 403 `FORBIDDEN_ROLE`. Sarah: то же → 204.
7. George: `DELETE /families/{id}/members/me` → 204, `user.family === null`.
